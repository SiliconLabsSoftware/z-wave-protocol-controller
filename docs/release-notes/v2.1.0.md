# ZPC Version 2.1.0 - Release Notes (Oct 29, 2026)

The Z-Wave Protocol Controller (ZPC) is a Linux and macOS host application for controlling Z-Wave networks through MQTT using a Silicon Labs Z-Wave - NCP Serial API Controller.

This release follows [v2.0.1](v2.0.1.md). It adds MQTT controls for more device functions, improves SmartStart and firmware update behavior, and changes how node IDs appear in MQTT reports. See [Impact and Migration](#impact-and-migration) before updating clients that read those reports.

## Release Summary

[Key Features](#key-features) · [API Changes](#api-changes) · [Bug Fixes](#bug-fixes) · [Chip Enablement](#chip-enablement) · [Known Issues](#known-issues-and-limitations) · [Impact and Migration](#impact-and-migration)

- **Control more Command Classes:** use MQTT to read values and control the Meter, Sensor Binary, Sensor Multilevel, Configuration, Schedule, Time, Node Naming and Location, and Thermostat Command Classes.
- **Get useful interview results:** `zpc/<home_id>/Interview/Report` now includes the root device's protocol and device-class information, Command Class lists, security details, and version information after its interview finishes.
- **Handle node IDs more easily:** ZPC publishes node IDs as decimal numbers in reports and topic paths. For node-specific command topic paths, clients can use decimal IDs or hexadecimal IDs prefixed with `0x`.
- **Improve setup reliability:** SmartStart can start as soon as a provisioned device announces its preferred protocol. After a firmware update, ZPC gives the device more time to restart before interviewing it.
- **Simplify development builds:** Linux and macOS use consistent build steps, with smaller runtime dependencies and broader automated test coverage.

### Enhancements

- For a provisioned device that supports both Z-Wave and Z-Wave Long Range, ZPC can begin SmartStart inclusion when the first Prime announces the preferred protocol. If it announces the less-preferred protocol first, ZPC continues discovery before choosing.
- When an endpoint interview ends, ZPC publishes `zpc/<home_id>/Interview/Report` with `node_id`, `endpoint_id`, and numeric `status` (`0` means success). A successful report is sent after the post-interview requests finish; failed or cancelled interviews also produce a report. The endpoint 0 report additionally includes `node_information` (device classes, protocol capabilities, Command Class lists, inclusion protocol, and granted keys) and `version_report` (Z-Wave library and protocol versions, firmware and hardware versions, and firmware target count). Other endpoint reports omit these two objects. See the [Device Interviewer MQTT API](https://github.com/SiliconLabsSoftware/z-wave-protocol-controller/blob/zpc-v2.1.0/components/device_interviewer/docs/device_interviewer.md#interviewreport) for the full fields and example.
- An exclusion request can include `{"node_id": 2}` to accept only that classic Z-Wave node. If a different node initiates exclusion, ZPC stops the operation and leaves that node in the network. Z-Wave Long Range node-specific exclusion is not supported; see [known issues](#known-issues-and-limitations).
- After a firmware update, ZPC adds a controller-selected margin to the device's advertised Wait Time before probing for reconnection. The margin is 5, 10, or 30 seconds depending on the advertised wait, giving slower-restarting devices more time before the reachability check and re-interview.
- CMake presets now provide consistent configure/build workflows across Linux and macOS. CI runs unit tests with AddressSanitizer and UndefinedBehaviorSanitizer under GCC and Clang; separate sanitizer builds include ThreadSanitizer. A Clang coverage job checks line and branch coverage, with 90% thresholds for components outside the documented exemption list.
- The Paho MQTT C++ client library is updated from 1.5.3 to 1.6.0. Debian packages now depend on libc and OpenSSL at runtime; SQLite, fmt, yaml-cpp, and nlohmann/json are built into ZPC or provided as headers. Sanitizer packages declare their required sanitizer runtime libraries.
- Supported compiler builds enable `-fstack-protector-strong`; debug builds also initialize automatic variables with a pattern. Google Test and Google Mock are integrated into the project, with new tests covering CRC, Meter, Sensor Binary, Switch Binary, Schedule, and Thermostat Command Class implementations.

## API Changes

### New APIs

| MQTT interface | What it does |
|--------------------------|-----------|
| New Command Class topics | Added support for Meter, Sensor Binary, Sensor Multilevel, Configuration, Schedule, Time, and Thermostat Command Classes, including their corresponding MQTT topics for reading values and controlling devices where applicable. See the [MQTT API Index](https://github.com/SiliconLabsSoftware/z-wave-protocol-controller/blob/zpc-v2.1.0/components/mqtt_api/doc/mqtt_api_index.md). |
| Node naming topics | Get or set a node's display name with `NodeNamingNodeNameGet/Set`; ZPC publishes the response on `NodeNamingNodeNameReport`. See the [Node Naming MQTT interface](https://github.com/SiliconLabsSoftware/z-wave-protocol-controller/blob/zpc-v2.1.0/components/command_classes/command_class_node_naming/doc/generated/command_class_node_naming_mqtt_interface.md). |
| Node exclusion with a specified node ID | Add `node_id` to a normal `Network/Node/Remove` request to make ZPC accept only that classic Z-Wave node during exclusion. See the [Network Management MQTT API](https://github.com/SiliconLabsSoftware/z-wave-protocol-controller/blob/zpc-v2.1.0/components/network_manager/doc/network_management_mqtt_api.md). |

### Modified APIs

- Published node IDs now use decimal numbers. Node-specific MQTT topic paths accept decimal IDs or hexadecimal IDs with a `0x` prefix; for `node_id` values inside JSON payloads, follow the format documented for that API. Update clients that expect hexadecimal node IDs in reports or topic paths.
- `zpc/<home_id>/Interview/Report` is an existing topic. This release adds `node_information` and `version_report` to the report for endpoint 0; clients can use those fields after the interview instead of making a separate request to `Network/Node/List` for the root-device details.

## Impact and Migration

v2.1.0 works with networks created by v2.0.1. No database migration is required.

Published node IDs now use decimal numbers in JSON reports and node-specific topic paths. Update clients that expect hexadecimal IDs in reports or topic paths. When sending to a node-specific topic, clients may use a decimal ID or a hexadecimal ID with a `0x` prefix. A `node_id` field inside a JSON command payload follows that API's documented format.

New Command Class MQTT topics can be adopted as needed. Existing clients can continue using their existing topics.
